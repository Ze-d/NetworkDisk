# 文件上传与下载：学习重点与面试亮点

本文提炼项目文件模块中最值得学习、也最适合在面试中讲述的工程实践。重点不在于“实现了上传接口”，而在于如何处理大文件上传的可靠性、一致性与性能问题。

## 1. 真实文件与用户目录项分层建模

项目将文件拆为两层：

| 模型 | 职责 |
| --- | --- |
| `FileDO` | 管理真实文件路径、文件大小、`identifier`、后缀和预览 MIME |
| `UserFileDO` | 管理用户文件名、父目录、权限、目录结构，并以 `realFileId` 引用 `FileDO` |

这解决了“同一份内容如何在多个目录或业务场景出现”的问题：

- **秒传**：复用已有 `FileDO`，仅创建 `UserFileDO`；
- **复制**：通常复制用户目录项及其层级，不复制文件字节；
- **移动、重命名、回收站**：修改用户视图，不影响真实文件内容；
- **权限控制**：以 `UserFileDO.userId` 为边界校验用户是否有权操作。

面试表述：

> 我把物理文件和用户目录视图拆分建模。真实字节由 `FileDO` 管理，用户目录项由 `UserFileDO` 管理并通过 `realFileId` 关联。这样秒传和复制不需要重复保存文件内容，目录操作也不会影响底层真实文件。

## 2. 分片上传：幂等、断点续传和并发控制

当前前端按 1MB 进行分片、最多 3 路并发；每个片提交文件标识、总片数、片号和大小。服务端在 `FileChunkServiceImpl.saveChunkFile` 中处理临时分片。

### 幂等性

网络超时后，客户端无法确认服务端是否已收到分片，通常会重试。若每次重试都直接写盘，会造成重复数据或唯一键冲突。

因此服务端先检查当前用户、当前 `identifier`、当前 `chunkNumber` 是否已有有效分片：

```java
if (checkChunkUploaded(context)) {
    doJudgeMergeFile(context);
    return;
}
```

存在即视为成功，不重复写临时文件和分片记录。这是“至少一次请求投递”场景中最重要的接口设计原则。

### 断点续传

客户端可查询已成功上传的片号，只补传缺失片。临时片以 `identifier + 用户 + 片号` 关联，避免不同用户或不同文件的上传状态混用。

### 并发控制

`UserFileServiceImpl.chunkUpload` 用以下分布式锁串行化同一文件的临界操作：

```java
@DistributeLock(
    scene = "FILE_CHUNK_UPLOAD",
    keyExpression = "#context.userId + '-' + #context.identifier"
)
```

它避免两个并发请求同时判断“该片不存在”，随后都写盘或同时插入记录。

面试表述：

> 分片上传中我重点处理了网络重试和并发竞态。服务端以用户、文件标识和片号标识一个分片，先做有效片检查保证幂等；同一文件的分片请求再用分布式锁保护临界区，因此重试不会重复写入，并发也不会产生重复分片记录。

## 3. 临时分片的过期与清理

`FileChunkDO` 是未完成上传的临时状态，而不是永久文件。每片写入时会设置过期时间；当前默认保留 1 天。

过期处理主要解决两个问题：

1. 用户中断上传后，临时文件和数据库记录不能无限占用磁盘与表空间；
2. 已过期或逻辑删除的记录可能仍占用唯一键，阻止同一文件片的重新上传。

因此上传前会清理同一 `(identifier, chunkNumber, createUser)` 下的无效记录，再判断是否有有效片可复用。

面试表述：

> 我将 chunk 设计为有生命周期的临时缓存。重传前会清理过期和逻辑删除记录，既避免临时存储膨胀，也避免业务上认为分片无效、数据库唯一键却仍阻止插入的状态矛盾。

## 4. 合并的顺序性与一致性

分片上传本身是并发、乱序的；数据库查询也没有默认顺序。因此合并前必须显式排序：

```java
chunkRecoredList.stream()
    .sorted(Comparator.comparing(FileChunkDO::getChunkNumber))
    .map(FileChunkDO::getRealPath)
```

之后存储引擎按顺序拼接得到最终物理文件，删除临时分片及记录，再创建 `FileDO` 与 `UserFileDO`。

若不排序，最终文件大小可能仍然正确，但字节顺序错误，文件内容会损坏。

面试中可以进一步说明改进方向：

> 合并不能只依赖客户端通知，还应在服务端复核分片数量、片号连续性和最终文件大小，并用与上传相同粒度的分布式锁保证重复 merge 幂等。

## 5. 下载和预览的流式输出

下载和预览都会通过 `StorageEngine.realFile` 将真实文件写到 `HttpServletResponse` 输出流。底层读取相同，差别只在响应头：

- 下载使用 `application/octet-stream` 和 `Content-Disposition: attachment`；
- 预览使用文件的 MIME 类型，不设置 attachment。

这样做的价值：

- 不必把整个文件加载进 JVM 堆内存；
- 可以边读存储边回写 HTTP 响应，适用于大文件；
- 本地磁盘、OSS、FastDFS 都实现同一 `StorageEngine` 接口，上层业务无需感知存储介质。

面试表述：

> 下载和预览复用流式读取链路，只通过响应头区分浏览器行为。服务端直接将存储输入流写入响应输出流，避免大文件导致 JVM 内存峰值；存储层通过接口抽象，因此切换本地盘或对象存储不会影响业务层。

后续可以支持 HTTP Range 和 `206 Partial Content`，实现音视频拖动播放和大文件按需读取。

## 6. 目录树与非法移动/复制保护

目录树一次查询当前用户的全部有效文件夹，再按 `parentId` 在内存构建，避免递归查询形成 N+1 SQL。

复制或移动时，系统会收集源目录和所有子孙目录；目标目录若在该集合中则拒绝操作：

```text
禁止将 A 移动/复制到 A、A/B、A/B/C
```

这防止移动导致目录环，以及复制递归造成无限嵌套。

面试表述：

> 对目录移动和复制，我会先递归计算源目录的子树，并禁止目标目录落入该子树。这样既保证树结构无环，也避免复制时递归进入自己造成无限增长。

## 一分钟项目介绍模板

> 我在网盘项目中重点实现了大文件上传与读取链路。模型上把真实文件和用户目录项拆分，秒传和复制只复用真实文件引用。上传侧采用分片并发上传，客户端用全文件 MD5 标识文件，服务端通过幂等检查、分片过期清理和分布式锁处理网络重试、断点续传和并发竞争。全部分片完成后按片号排序合并，再生成正式文件与用户目录项。下载和预览则采用流式输出，避免大文件占满 JVM 内存，仅通过响应头区分保存和在线展示。

## 面试准备优先级

1. 分片上传的幂等性、断点续传与分布式锁；
2. 过期分片清理和物理存储/数据库一致性；
3. 合并的顺序性、完整性校验与重复调用处理；
4. 流式下载、预览和 HTTP Range 的演进；
5. `FileDO` / `UserFileDO` 分层模型及其对秒传、复制的价值。
