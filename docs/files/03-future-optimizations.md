# 文件模块：后续优化建议

以下建议按风险和收益排序，基于当前代码实现提出。

## P0：正确性与安全性

### 1. 修复单文件上传未真正调用存储引擎的问题

**现状**：`FileServiceImpl.storeMultipartFile` 创建 `StoreFileContext` 后未执行 `storageEngine.store(storeFileContext)`，却直接读取 `realPath`。

**风险**：`POST /file/upload` 可能保存带空路径的 `FileDO`，后续下载和预览无法读取文件。

**建议**：在设置上下文字段后调用存储引擎，并仅在成功后回填路径。

```java
storageEngine.store(storeFileContext);
context.setRealPath(storeFileContext.getRealPath());
```

同时为单文件上传增加集成测试：上传后断言 `FileDO.realPath` 非空、目标文件存在且能被下载。

### 2. 在合并接口复核分片完整性，并给合并加锁

**现状**：READY 主要由上传接口返回，`/file/merge` 本身仅查询现有分片后合并；同一文件的 merge 操作没有显式分布式锁。

**风险**：客户端重复调用或恶意提前调用 merge，可能造成不完整文件、重复 `FileDO` 或重复 `UserFileDO`。

**建议**：

1. merge 使用与上传相同的 `(userId, identifier)` 锁；
2. 分片记录保存或合并请求携带总片数；
3. 合并前检查数量等于总片数、片号集合完整且连续；
4. 校验实际合并大小等于 `totalSize`；
5. 为已成功合并的 `identifier` 建立可幂等识别，重复调用直接返回已有结果。

### 3. 补全复制、移动的资源归属校验

**现状**：复制/移动会验证目标是目录，也会防止目标落入源目录自身或子孙目录；但 `getById(targetParentId)` 和 `listByIds(fileIdList)` 未在查询层显式限定当前用户。

**风险**：若加密 ID 被获得，可能尝试以他人目录作为目标或操作他人文件。

**建议**：源记录和目标目录查询均加 `user_id = context.userId`、`deleted = NO`，并验证请求的 ID 数量与实际查到的记录数量一致。把权限校验收敛为可复用方法，避免不同操作遗漏。

## P1：数据一致性与可靠性

### 4. 建立“物理存储—数据库”失败补偿机制

**现状**：物理文件或分片通常先写存储，再写数据库。`FileServiceImpl.doSaveFile` 中数据库失败后的物理删除仍是 TODO。

**风险**：数据库事务回滚时遗留孤儿文件；存储写成功、元数据失败时难以人工排查。

**建议**：短期实现同步删除补偿并记录失败任务；中期使用 outbox/可靠消息记录待清理任务，由定时任务重试；长期将对象存储路径按上传会话隔离，并按状态异步清扫。

### 5. 完善临时分片的全量过期清扫

**现状**：新请求到来时会清理相同唯一键下的过期分片，但长期无人继续上传的任务不会主动触发清理。

**风险**：临时分片和 `file_chunk` 表会持续增长。

**建议**：增加定时任务扫描 `expiration_time <= now` 的记录，删除物理临时文件后物理删除记录；任务应记录处理数量、失败路径，并支持重试。

### 6. 消息发送采用 Outbox，而不只依赖 afterCommit 回调

**现状**：AI warmup 消息在 `afterCommit` 中发送，能避免未提交读取，但进程在提交后、发送前崩溃时，消息会丢失。

**建议**：事务内写 outbox 表，后台可靠投递并记录投递状态；消费者按 `userFileId` 保证幂等。这样能同时保证“提交后发送”和“最终一定发送”。

## P2：性能与体验

### 7. 将本地分片合并改为真正的流式/零拷贝复制

**现状**：`LocalStorageEngine.doMergeFile` 通过 `FileUtil.appendWrite`，其内部使用 `Files.readAllBytes` 读取每个片。

**风险**：单片较大时会产生明显堆内存峰值，多个合并任务并发时可能造成 GC 压力甚至 OOM。

**建议**：采用 `FileChannel.transferTo/transferFrom`，或固定缓冲区的流式复制；同时限制合并并发度。

### 8. 支持 HTTP Range，实现音视频与大文件的真正按需读取

**现状**：服务端已流式输出，但没有处理 `Range` 请求。前端以 Blob 接收，浏览器仍可能先下载完整文件。

**建议**：实现 `Accept-Ranges`、`Range`、`Content-Range` 和 `206 Partial Content`，并为 OSS 存储映射范围读取。这样视频可以拖动播放，预览大文件无需整文件下载。

### 9. 文件夹树和子目录校验优化为可扩展查询

**现状**：构树和“目标是否位于源目录子树”都将当前用户全部目录加载到内存。

**风险**：用户目录量达到几十万时，内存和递归遍历会成为瓶颈；异常脏数据还可能导致递归循环。

**建议**：中小规模保留现方案，但加 `visited` 集合防循环；大规模时采用 closure table、物化路径或递归 CTE，仅查询所需子树。

### 10. 让搜索请求使用强类型集合

**现状**：`fileTypes` 是分隔符字符串，历史上已出现解析分隔符错误。

**建议**：改为 JSON 数组 `List<Integer> fileTypes`，在 API 层校验合法文件类型；为全量、空列表、单项、多项、非法值建立 Controller 测试。

## 推荐实施顺序

1. 修复单文件上传存储调用；
2. 强化 merge 的锁、完整性校验和幂等；
3. 补复制/移动权限校验；
4. 实现物理存储失败补偿和分片定时清理；
5. 优化分片合并和 Range 预览；
6. 随数据规模演进目录树与搜索接口设计。
